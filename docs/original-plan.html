Study Library

A personal course library for four History modules. It holds every reading alongside the notes and recordings from each lecture and class. It runs on laptops and phones and keeps them in sync.

Plan and architecture. Working draft, 6 October 2026.

1Purpose and scope

Study Library replaces the current Zotero setup for course work. It is built for one person and is not a reference manager.

It has four jobs:

  • Store every course PDF and make it pleasant to read, with highlights and comments.
  • Hold lecture notes and class notes, organised by week and session.
  • Record sessions, or take in Moodle recordings, and transcribe them.
  • Gather evidence from the readings against each seminar question.

Out of scope: citations, bibliographies, a Word plugin, a browser connector, sharing, and editing Word or PowerPoint files inside the app. Word and PowerPoint files are converted to PDF for reading instead.

3How the course is organised

A module runs for 22 weeks: AT1 to AT11 and WT1 to WT11. Reading weeks stay in the list but hold no sessions.

Each module has a session pattern, set when the module is created. HY335 might have a lecture and a seminar each week. A module that merges the two has one combined session. Creating a module generates all 22 weeks with their sessions already in place. Any week can be changed by hand, for a cancelled class or a guest lecture.

Readings belong to the week, since they serve every session in it. One reading can belong to several weeks without being stored twice. Slides and recordings belong to a session, as do its notes. Seminar questions belong to a seminar or a combined session.

4Interface

Screens

Module list
One continuous list per module, grouped by week. It keeps the shape of the current Zotero list without the title prefixes. Weeks collapse, and a jump bar goes straight to any week. Each week row shows progress, such as "2 of 4 read". The list opens at the week you last looked at.
Week page
Readings first, with primary sources grouped below the secondary readings. Then one section per session, in timetable order.
Week across modules
Pick a week number to see that week for all four modules together.
Reader
The PDF beside your notes. On a phone the notes open as a sheet over the page.
Session mode
The screen for a live lecture or class. It pairs the notes editor with the slides and puts the record control in the header.
Import
Bulk upload for a whole module, with a review table before anything is saved.
Search
One box across readings, transcripts, notes and highlights. Each result opens at the right page or moment.

Empty states

  • A section renders only when it has content. A week without primary sources has no primary sources heading.
  • No placeholder text and no zero counts. Progress counts only what exists.
  • Weeks are collapsed by default. A collapsed week shows its title and how many readings it holds.
  • Adding content never needs an empty slot. Drop a file anywhere on a week, or use the single Add control in each session header.
  • Recording starts from session mode, so record buttons don't repeat down every week.
  • Work in progress shows quietly, such as "Transcribing". A failure shows a retry. Nothing else announces that something is absent.
  • Generated titles are built only from fields that exist. No empty brackets or stray "pp.".

Visual rules

  • Hierarchy comes from type size, weight and thin rules. No boxes or shadows.
  • Zero border radius throughout, with #185FA5 as the accent.
  • The app follows the system light or dark setting. The reader has its own themes on top.

5The reader

The reader is built on PDF.js. Pages render only as they come close to the screen, and rendered pages are cached, so long scans scroll smoothly. react-pdf-highlighter-extended is a reasonable starting point for selection and highlighting. If it limits performance, replace it with a custom highlight layer over PDF.js. Zotero's own reader is open source and worth studying for how it handles very long documents.

Zoom works in steps and by pinch. Phones open pages at full width. Sepia and dark themes sit alongside the plain page. Sepia tints the page with a CSS filter. Dark inverts the page and rotates the hue, which keeps images and maps readable.

A highlight has a colour and an optional comment, and can be filed to a seminar question. It is stored as a page index plus rectangles in PDF coordinates. That survives zoom and theme changes. It also matches the format Zotero uses, which makes migration straightforward.

Each reading remembers the last page you were on. Under last-write-wins, the device you used most recently decides where every device opens.

Text selection needs a text layer. Born-digital PDFs have one. Scans get one from OCR in the worker. Until then a scan can be read but not highlighted, and its row says so quietly.

6Notes and seminar questions

Notes use BlockNote, a block editor built on TipTap. It gives Notion-style blocks with slash commands and drag handles.

Each block is its own row with a stable id. When a note changes, only the changed blocks are written. Deleted blocks are kept as tombstones so deletions sync like any other edit. Block order uses fractional indexing: a block inserted between two others gets a position key that sorts between theirs, so nothing is renumbered.

Two custom features matter. A highlight block quotes a passage from a reading and opens the reader at that spot. A timestamp is attached to every block written during a recording. It stays invisible until you hover, when a small play control appears.

Seminar questions

Questions are pasted from Moodle and split by line. Each question opens as a panel in two parts. The top lists every highlight filed to it, ordered by reading and then by page. Below that is the answer note. Drag any filed highlight into the answer to quote it.

Highlights that are not filed stay with their reading as usual.

7Recording and transcription

Live recording

Recording uses the browser's MediaRecorder API and captures audio only. Chrome records WebM with Opus and Safari records MP4 with AAC. The worker converts both to the same format.

Audio is recorded in one-minute chunks. Each chunk is written to IndexedDB first, then uploaded. It is removed from the device only once the server confirms it. A dropped connection or a crashed tab costs at most a minute.

The Screen Wake Lock API keeps the laptop awake for the length of the session.

Every note block written during the recording stores the recording id and its offset in seconds. Clicking the block plays from that moment.

Press a key when the lecturer moves to the next slide and the app stores a slide mark. If the slides are open in session mode, turning the page stores the mark automatically.

Moodle recordings

For lectures you miss, drop the Moodle audio or video file onto the session. The worker extracts the audio with ffmpeg and discards the video. Notes taken while watching use the playback position as their offset, so they link to the audio in the same way.

Transcription

Transcription runs after the session rather than live. The worker splits the audio into ten-minute pieces to stay within API file limits, transcribes each one, and joins the results with corrected timestamps.

Transcripts are stored as segments with start and end times. Clicking a segment plays the audio from there. Slide marks divide the transcript by slide, so each slide shows what was said about it.

Start with a hosted transcription API. faster-whisper running on the worker is the fallback if cost or privacy matters more later.

Once a transcript is ready, a second job writes a summary of the session with the Claude API. It appears above the transcript. Where slide marks exist, it adds a sentence or two for each slide. Summaries can be regenerated and are included in search.

The session header shows a recording's state only while it is being processed or if it has failed. A failure comes with a retry.

Consent

Check LSE's rules on recording teaching before relying on live recording. Ask before recording seminars where classmates speak. Recordings stay private to your account.

8Importing readings

Bulk import

  1. Choose a module and drop a folder of PDFs onto it.
  2. Each filename is parsed with your existing naming convention.
  3. A review table lists every file with its week, type, position and title. Correct anything inline.
  4. Confirm once. Files that didn't match go to the module's unsorted tray, which only appears when it holds something.
  5. Files upload in parallel, and each upload is resumable. A SHA-256 hash is computed first, and a file already stored is linked rather than uploaded again.
  6. Processing jobs are queued in week order. Opening a reading that hasn't been processed moves it to the front.

Migrating from Zotero

  • Work from a copy of zotero.sqlite and the storage folder, never the live database.
  • Item titles go through the same parser as bulk import.
  • Each "00" note sets its week's title. Its content becomes notes on the week's first session. Zotero notes are HTML, which BlockNote can convert into blocks.
  • Zotero keeps PDF annotations in its itemAnnotations table, with a page index and rectangles in PDF coordinates. They map directly onto highlights, keeping their colours and comments.
  • Zotero item keys are stored, so a second run updates records instead of duplicating them.

Worker and jobs

The worker uses OCRmyPDF, LibreOffice in headless mode, ffmpeg and PyMuPDF. It takes work from a jobs table in Postgres.

JobInputOutput
extract_textPDFPage text for search. Flags PDFs with no text layer for OCR.
ocrScanned PDFA compressed PDF with a text layer.
convert.pptx or .docxA PDF for reading. The original is kept.
prepare_audioLive chunks or a Moodle fileOne Opus audio file for playback.
transcribeAudioTimed transcript segments.
summariseTranscript and slide marksA session summary, with notes per slide where marks exist.
backupDatabaseA nightly dump stored in R2.

Jobs are claimed with select ... for update skip locked, so a second worker could run without conflicts. Each job retries with backoff and is marked failed after five attempts. Jobs run in week order, and opening an unprocessed reading moves its job to the front.

10Sync

Sync follows one rule: the most recent edit to a row wins.

  • Every row gets a UUIDv7 generated on the device, so anything can be created offline.
  • Rows carry two timestamps. modified_at is set by the device at the moment of the edit and decides conflicts. synced_at is set by a database trigger when the row is written and drives pulling.
  • Edits wait in an outbox in IndexedDB. When online, the outbox sends batches to one Postgres function, apply_changes, called through Supabase RPC. It applies each row only if it is newer than the stored version.
  • Each device keeps a cursor: the latest synced_at it has seen. On reconnecting it fetches every row written since. While online, Supabase Realtime pushes changes as they happen.
  • Deletions set deleted to true rather than removing the row. Tombstones older than 90 days are purged nightly.
  • Files never change after upload, so they never conflict. All edits are stored in rows.
  • Device clocks are kept in sync by the operating system. A few seconds of skew only matters for edits made seconds apart on two devices.

The core of apply_changes for one table:

insert into note_blocks as t
  (id, user_id, note_id, position, type, content, modified_at, deleted)
values
  ($1, $2, $3, $4, $5, $6, $7, $8)
on conflict (id) do update
set position    = excluded.position,
    type        = excluded.type,
    content     = excluded.content,
    modified_at = excluded.modified_at,
    deleted     = excluded.deleted
where excluded.modified_at > t.modified_at;

Offline

Rows are small, so every device keeps a full copy of them. Files are cached selectively. Laptops can cache every PDF, since a year's readings fit comfortably on disk. Phones cache a week's files when you open it, along with the following week's. Android gives web apps generous storage, so this can be widened to a whole term if it proves useful. Recordings stream rather than cache.

11Data model

Every synced table also carries user_id, modified_at, synced_at and deleted. They are left out below for readability. Row-level security limits every table to your user id.

create table modules (
  id uuid primary key,
  code text not null,
  title text,
  session_pattern jsonb not null,
  description jsonb,
  last_opened_week_id uuid,
  position text not null
);

create table weeks (
  id uuid primary key,
  module_id uuid not null references modules,
  term text not null check (term in ('AT', 'WT')),
  number int not null check (number between 1 and 11),
  title text,
  is_reading_week boolean not null default false
);

create table sessions (
  id uuid primary key,
  week_id uuid not null references weeks,
  kind text not null check (kind in ('lecture', 'seminar', 'combined')),
  title text,
  position text not null
);

create table files (
  id uuid primary key,
  sha256 text not null unique,
  r2_key text not null,
  mime text not null,
  bytes bigint not null,
  page_count int,
  text_status text not null default 'pending'
);

create table items (
  id uuid primary key,
  kind text not null check (kind in ('secondary', 'primary', 'slides')),
  author text,
  title text not null,
  source text,
  pages text,
  year int,
  doc_date text,
  file_id uuid references files,
  original_file_id uuid references files,
  zotero_key text,
  last_page int,
  read_status text not null default 'unread'
);

create table week_items (
  id uuid primary key,
  week_id uuid not null references weeks,
  item_id uuid not null references items,
  session_id uuid references sessions,
  position text not null
);

create table questions (
  id uuid primary key,
  session_id uuid not null references sessions,
  body text not null,
  position text not null
);

create table highlights (
  id uuid primary key,
  item_id uuid not null references items,
  page int not null,
  rects jsonb not null,
  body text,
  colour text not null,
  comment text,
  question_id uuid references questions,
  zotero_key text
);

create table recordings (
  id uuid primary key,
  session_id uuid not null references sessions,
  source text not null check (source in ('live', 'upload')),
  file_id uuid references files,
  duration_seconds numeric,
  slide_marks jsonb not null default '[]',
  summary jsonb,
  status text not null default 'recording'
);

create table notes (
  id uuid primary key,
  session_id uuid references sessions,
  item_id uuid references items,
  question_id uuid references questions,
  check (num_nonnulls(session_id, item_id, question_id) = 1)
);

create table note_blocks (
  id uuid primary key,
  note_id uuid not null references notes,
  position text not null,
  type text not null,
  content jsonb not null,
  recording_id uuid references recordings,
  offset_seconds numeric,
  highlight_id uuid references highlights
);

create table page_text (
  file_id uuid references files,
  page int,
  body text,
  tsv tsvector generated always as (to_tsvector('english', body)) stored,
  primary key (file_id, page)
);

create table transcript_segments (
  id uuid primary key,
  recording_id uuid not null references recordings,
  start_seconds numeric not null,
  end_seconds numeric not null,
  body text not null,
  tsv tsvector generated always as (to_tsvector('english', body)) stored
);

create table jobs (
  id bigint generated always as identity primary key,
  type text not null,
  payload jsonb not null,
  status text not null default 'queued',
  priority int,
  attempts int not null default 0,
  run_after timestamptz not null default now(),
  error text
);
  • position columns hold fractional index keys, which sort as text.
  • doc_date is free text because primary source dates vary in precision, from a full date to a single year.
  • week_items.session_id is set for slides and left empty for readings.
  • The check constraint on notes makes sure each note has exactly one parent.
  • page_text and transcript_segments are written only by the worker. They stay on the server for search, and a session's transcript is fetched when it is opened.
  • zotero_key makes repeat migrations safe.
  • modules.last_opened_week_id syncs, so every device opens a module at the week you last looked at.
  • recordings.summary holds the session summary and any per-slide notes.

12Build phases

Each phase leaves something usable. Effort is a rough guide in weeks of evenings.

  1. Phase 0. Foundations

    About one week.

    Repository, Supabase project, R2 bucket, schema and row-level security. Sign-in. The PWA shell. The sync engine: outbox, apply_changes, pull cursor and Realtime subscription.

    Done when a module created offline on the laptop appears on the phone after reconnecting.

  2. Phase 1. Library and reader

    About three weeks.

    Module creation with session patterns. The module list, week page and cross-module week view, following the empty-state rules. Bulk import with the parser, review table, unsorted tray, resumable uploads and deduplication. The reader with zoom, themes, highlights, comments and saved position. Zotero migration, including annotations.

    Done when the Autumn Term readings for all four modules are in, readable on both devices, with existing Zotero highlights intact.

  3. Phase 2. Processing worker

    About one week.

    The VPS and Docker setup. The job queue. OCR, LibreOffice conversion and page text extraction. Nightly backups to R2.

    Done when a scanned reading or a .pptx dropped onto a week becomes a highlightable PDF with no manual steps.

  4. Phase 3. Notes and questions

    Two to three weeks.

    BlockNote with block-level sync. The split view in the reader. Highlight blocks. Seminar questions, filing highlights and answer notes. Reading notes.

    Done when a seminar question shows highlights filed from several readings, and the answer written around them syncs between devices.

  5. Phase 4. Sessions and recording

    About two weeks.

    Session mode. Live recording with the local chunk buffer and wake lock. Timestamped blocks and slide marks. Moodle uploads with audio extraction. Playback that jumps from any note.

    Done when a lecture recorded on the laptop plays from the right moment when any note is clicked.

  6. Phase 5. Transcription and search

    One to two weeks.

    Transcription jobs with segment joining. The transcript view, divided by slide. Session summaries from the Claude API. Full-text search across page text, transcripts, summaries, notes and highlights.

    Done when a finished lecture shows its summary above the transcript, and searching for a phrase from it opens the transcript at the moment it was said.

  7. Phase 6. Polish

    Ongoing.

    The phone caching policy. Performance on very long scans. An empty-state audit across a full term of real data. A native Android build with Capacitor for phone recording, if it turns out to be needed. It can be installed directly from an APK, with no Play Store listing.

Keep using Zotero until Phase 3 is done. Then run the migration again to bring in anything added since. Zotero item keys are stored, so the second run updates records rather than duplicating them.
